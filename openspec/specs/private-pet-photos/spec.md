# Private Pet Photos Specification

## Purpose

Protects pet photos as owner-private resources while retaining the current filesystem-backed storage and existing user workflow.

## Requirements

### Requirement: Owner-authorized photo upload
Only an authenticated owner of a pet SHALL be allowed to upload or replace that pet's photo. The service MUST validate ownership independently of client-provided metadata.

#### Scenario: Owner uploads a valid photo
- **WHEN** an authenticated pet owner uploads a JPEG or PNG image no larger than 10 MB for their pet
- **THEN** the system stores the image and associates its opaque key with that pet

#### Scenario: Non-owner attempts upload
- **WHEN** an authenticated user uploads a photo for a pet they do not own
- **THEN** the system rejects the operation without modifying the pet or stored files

#### Scenario: Invalid photo input
- **WHEN** an owner uploads an unsupported file type or a file larger than 10 MB
- **THEN** the system rejects the upload without storing it

### Requirement: Owner-authorized photo retrieval
Only an authenticated owner of a pet SHALL be allowed to retrieve that pet's photo. Missing photos and photos inaccessible to the caller SHALL use indistinguishable not-found responses.

#### Scenario: Owner downloads a photo
- **WHEN** an authenticated owner requests their pet's stored photo
- **THEN** the system returns the image with its correct media type and private cache directives

#### Scenario: Foreign or missing photo
- **WHEN** an unauthenticated caller, a non-owner, or an owner requesting a missing photo attempts retrieval
- **THEN** the system returns a uniform not-found response without disclosing pet or photo existence

### Requirement: Safe filesystem object keys
Stored photo keys MUST be generated by the service, scoped beneath the authenticated owner, contain no client-controlled path segments, and use only an extension derived from an accepted media type.

#### Scenario: Filename contains path syntax
- **WHEN** a valid upload includes a filename containing path separators or traversal sequences
- **THEN** the stored object key is still generated beneath `pets/<owner-id>/` and does not contain the supplied path

### Requirement: Existing photo workflow remains compatible
The photo capability SHALL continue to use the configured filesystem backend and preserve readable existing photo associations during this change.

#### Scenario: Existing owner photo
- **WHEN** an owner requests a photo association created before deployment of this change
- **THEN** the system resolves it through the secured retrieval flow without requiring an object-storage migration
